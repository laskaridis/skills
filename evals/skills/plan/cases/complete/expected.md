- [intent_fidelity] Assess the actual meaning of BOTH the design and plan against the specification. Cover all required behaviors, error outcomes, constraints, and easily missed edge cases; introduce no unsupported behavior. Excluded capabilities mentioned only as exclusions are acceptable.
  A criterion ID in an array is not evidence that its behavior is implemented or verified. Cite specific task IDs, specification criterion IDs, and relevant text. Explain materially conflicting design/plan statements. Missing or unusable design/plan artifacts are ungradable.
  AC-001: new active reservation returns stable ID and correct event/attendee.
  AC-002: duplicate active attendee/event reuses ID and never consumes another seat even at capacity; EVENT_STARTED takes precedence at/after start.
  AC-003/004: full rejection is nonmutating; atomic capacity and duplicate handling under simultaneous calls.
  AC-005: unknown event and exact start boundary yield specified errors without mutation.
  AC-006/007: cancellation releases one seat, repeat releases none, missing ID has specified error.
  AC-008: original attendee rebooks with a fresh ID while cancelled history stays cancelled.
  AC-009: late active cancellation is refused without mutation; late repeat of cancelled is success; missing ID remains not found.
  AC-010/011: observable stable outcomes; controlled time; reproducible concurrency checks, no sleeps or network.
  In-process local service with in-memory state for one process; no application code exists.
  The planning agent must select justified module boundaries and interfaces; routine coding choices remain with the implementor. Respect essential atomicity, stable-outcome, and deterministic-testing constraints.
  Unsupported additions: waitlist; payments or refunds; seat selection or multi-seat reservations; notifications; authentication or authorization; HTTP endpoints or UI; database or restart persistence; event administration; expiry or background jobs.
- [design_drivers_and_decisions] Assess whether the design identifies the key architectural drivers grounded in the specification and explains their impact on consequential design decisions. Relevant drivers include in-process operation with one-process in-memory state, atomic capacity and duplicate guarantees (AC-002/004), event-start rules and controlled time (AC-005/009/011), and stable outcomes with no mutation on failure (AC-010). A list of generic quality attributes without an architectural consequence is insufficient.
  Identify material architectural risks and uncertainties, especially concurrent final-seat/duplicate handling and deterministic boundary-time behavior, with a credible mitigation or early validation task. Cite relevant design sections and task IDs. Evaluate the observable reasoning and outcome; do not require an internal self-evaluation transcript.
- [design_boundaries] Assess the affected modules and their boundaries in the design document. Identify the main reasons for change and a minimal set of coherent modules; explain each affected module's responsibility, collaborators/dependencies, published interfaces, and scope of change with rationale. Use the design template's relevant sections: references, key drivers, consequential decisions/trade-offs, and affected modules. Optional execution-flow and risk sections should appear only when useful; unchanged parts of existing modules need not be redescribed.
  Check that ownership of mutable reservation/capacity state, the coordination boundary for atomic capacity/duplicate guarantees, and the source of controlled time are identifiable. A single cohesive module or multiple modules are acceptable if responsibilities and cross-boundary consistency are justified. Do not require specific names, counts, classes, or architecture patterns. Cite concrete module/interface descriptions and unaddressed dependencies.
- [design_document_contract] The design document follows the standardized output contract, not just an unstructured architecture sketch: it references the supplied specification, identifies key drivers with their architectural consequences, records consequential decisions with rationale and trade-offs, and describes affected modules in terms of responsibility, collaborators, published interfaces, and scope/rationale. No unsupported references or empty template placeholders.
  Require relevant content, not repeated headings or generic principles. Optional API, schema, execution-flow, and risk sections appear only where useful; a greenfield feature with new modules needs meaningful module descriptions. Accept equivalent formatting and concise wording, without mandating class names, module counts, interface signatures, or detailed algorithms.
- [design_change_resilience] Assess whether the proposed boundaries actually support change locality, information hiding behind small meaningful interfaces, independent testability, and incremental evolution. Module names and claims of "low coupling" or "extensibility" are not sufficient evidence.
  Capacity/duplicate-rule probe: changing allocation or deduplication policy should have a clear owning or coordinating boundary; unrelated callers should not need to modify internal seat counts, locks, indexes, or mutable reservation state.
  Time-rule probe: changing event-start rules or supplying a test clock should have an identifiable location and remain deterministically testable at exact boundaries without wall-clock sleeps; do not require a separate time module if a cohesive design is sufficient.
  Representation probe: changing how in-memory reservations are stored should preserve published reserve/cancel outcomes, cancellation history, and fresh-ID rebooking without propagating representation changes to consumers.
  Assess whether interfaces are small but meaningful and hide internal state, and whether reservation/cancellation behavior can be verified locally and evolved in incremental slices. Infer change impact from the design and tasks; do not demand a change-impact table, particular implementation pattern, explicit evaluation transcript, or detailed signatures. Cite concrete module, interface, and task evidence. Cohesion, coupling, and proportionality are graded separately by `design_coupling_cohesion` and `design_simplicity`.
- [design_coupling_cohesion] Assess, from the module descriptions, interfaces, and dependencies in the design, whether each module has one functional purpose and changes for one reason (cohesion), and whether dependencies are explicit, necessary, directed at stable contracts, free of cycles, and free of coupling to another module's implementation details such as its internal state, locks, indexes, or storage layout (coupling). Names or claims of "low coupling" or "high cohesion" are not evidence: cite concrete module responsibilities, published interfaces, and dependency statements, and name any mixed responsibilities, hidden or circular dependencies, or reach-through to internals.
  A single cohesive module is acceptable; do not require multiple modules, specific names, counts, or patterns. In that case assess whether the internal responsibilities described in the design and tasks (for example reservation state and capacity/duplicate rules, the event-start time source, and outcome reporting) are separated and relate only through stated contracts, without demanding more modules.
  Do not re-assess template conformance (`design_document_contract`) or whether state ownership and consistency boundaries are identifiable (`design_boundaries`); assess whether the described responsibilities and dependencies are cohesive and loosely coupled.
- [design_simplicity] Assess conceptual simplicity and proportionality: the design uses the fewest concepts, modules, layers, and abstractions necessary for this in-process, single-process, in-memory feature. A module or abstraction is justified only if it isolates an external boundary or a responsibility that would otherwise be mixed into a functionally unrelated module; cite the design text that justifies each one.
  Fail speculative layers, indirection, pluggable or generic frameworks, or machinery for excluded capabilities (see the unsupported additions listed in `intent_fidelity`, such as persistence, background jobs, or transport layers) that the specification does not require. Required atomicity, stable outcomes, and controlled time are legitimate concerns, not over-engineering.
  Pass a single cohesive module or a small justified set. Do not require a particular architecture, module count, or pattern, and do not fail a design merely for having several modules if each is justified. Cite concrete modules, abstractions, or layers and their stated rationale.
- [verifiability] Every task has concrete, observable, locally verifiable completion criteria tailored to its outcome. “Works”, “tests pass”, “implement correctly”, or a list of criterion IDs is insufficient. Check boundary time, state nonmutation, duplicate/capacity, and deterministic concurrency evidence.
  Task-specific concrete inputs, outputs, invariants, and local checks; not merely criterion IDs or tests pass.
  Every task states its own observable outcome even when multiple criteria share a task.
  Checks collectively distinguish reuse versus fresh IDs, exact start boundaries, nonmutation on failure, released capacity, and concurrency consistency.
- [actionability] Tasks are cohesive vertical slices of value, traceable to the specification and executable autonomously. Necessary prerequisites are acceptable. Gratuitous file names, helper signatures, algorithms, code snippets, class layouts, or framework choices that constrain the implementor fail this requirement.
  The planning agent should establish justified module boundaries, responsibilities, interfaces, and consequential constraints in the design; the implementation agent retains routine coding choices. Atomicity, small coherent interfaces, in-memory state, and controlled time are legitimate constraints, not excessive prescription.
  Accept valid alternative architectures and decompositions: there is no reference architecture, required task count, or mandated task order. Do not penalize an implementation-neutral boundary or infer a missing prerequisite from a preferred decomposition.
- [dependency_correctness] Required prerequisites are explicit or transitively reachable. A task may provide its own prerequisite within one cohesive slice. Missing edges and unjustified ordering constraints both count as failures. Do not assume numbering, array order, or prose implies a dependency edge.
  Tasks exercising cancellation need creation/state capability, either within the same cohesive task or through transitive dependencies.
  Rebooking, released-seat, duplicate-at-capacity and concurrent final-seat checks need their corresponding reservation/capacity capabilities.
  Cross-capability verification must depend on capabilities it verifies, or be included with those capabilities.
  Independent high-risk work should be scheduled as early as its dependencies allow. Do not require a fixed task count, architecture, layers, or order of independent capabilities. Judge transitive dependencies and alternative decompositions on their merits.
